# Phase 03.1: UI Polish - Research

**Researched:** 2026-04-09
**Domain:** Frontend (CSS-only) retrofit of Jinja2 + HTMX templates — no JS build step
**Confidence:** HIGH

## Summary

Phase 03.1 is an almost entirely CSS-driven retrofit. The 507-line UI-SPEC.md already locks every visual and interaction decision (tokens, palette, typography, components, copy, HTMX behaviour, a11y gates). Research was therefore scoped to **implementation gaps** the spec cannot answer on its own: the exact shape of the current templates, what CSS classes/markup the Phase 2 & 3 tests pin to, how icons/fonts get delivered inside Docker + a slim Python image without a build step, and how to make Nyquist validation mechanical.

Findings: current templates are already well-structured — nav, stat cards, expiring widget, license table (including HTMX partial), license form, license detail, and 404 — and the class names the spec wants to reuse (`.stat-card`, `.license-table`, `.status-*`, `.status-badge`, `.detail-*`, `.form-*`, `.btn`, `.actions-cell`) are all present. The existing `static/css/app.css` is 189 lines and can be wholesale rewritten. The main risk is **tests that assert on specific substrings** (class names, HTMX attributes, Russian copy, product names). Every assertion is a contract the executor MUST preserve. A complete inventory is in §Test Contract Inventory below.

**Primary recommendation:** Execute as a tightly-scoped CSS rewrite + minimal Jinja edits. Introduce a single token-driven `app.css` on `:root`, load Google Fonts via CDN in `base.html`, deliver icons as an inline SVG symbol sprite via a `{% include "partials/icons.html" %}` mounted once in `base.html` (then referenced with `<svg><use href="#icon-name"/></svg>`), and add a thin Jinja macro file for the `.status-badge` pill so the executor only writes its icon-plus-label pattern once. Every test assertion listed in §Test Contract Inventory must survive verbatim.

## User Constraints (from UI-SPEC.md — treat as CONTEXT.md equivalent)

> No separate CONTEXT.md exists for this phase; the approved UI-SPEC.md (status: approved, reviewed 2026-04-09) is the locked decision record. Quoted verbatim.

### Locked Decisions
- **Stack:** Plain CSS only. No Tailwind, no PostCSS, no preprocessor, no JS build step. Single `static/css/app.css` rewrite, ~500 lines max.
- **Fonts:** Inter (400/600/700) + JetBrains Mono (400) via Google Fonts CDN with `display=swap`, preconnect hints, loaded in `base.html` BEFORE the stylesheet link.
- **Icons:** Lucide static SVG, copy-pasted inline (no runtime fetch, no JS). Reserved set of 12: `layout-dashboard`, `plus`, `pencil`, `trash-2`, `chevron-up`, `chevron-down`, `search`, `alert-triangle`, `check-circle-2`, `x-circle`, `calendar`, `arrow-left`. No emoji.
- **Style family:** Flat / data-first / subtle-border (Linear / Grafana / Vercel aesthetic). No gradients, no glassmorphism, no decorative shadows. Borders do the work.
- **Spacing scale:** Strict 8-point — `4, 8, 16, 24, 32, 48, 64`. **12px removed entirely, no exceptions.**
- **Typography:** Exactly 4 sizes (12/14/18/24) and 2 weights (400/600). Weight 500 removed. Tabular nums mandatory on `.license-table td`, `.stat-card .count`, `.days-badge`, numeric `.detail-value`.
- **Palette:** "Slate Ops" — slate-50/100/200/300/500/700/900 + surface white + accent-600/700 blue + three semantic status triples (active/warning/expired) + destructive. All HEX values locked in spec.
- **60/30/10:** 60% slate-50/100, 30% white surface + slate-900 nav, 10% accent-600 on reserved list only (primary CTA, focus ring, active sort, current-nav underline, breadcrumb hover link). Accent used **nowhere else**.
- **Density:** Compact — 36px table row content height, 32px primary button, 28px table inline action button, 36px form input, 56px top nav.
- **Copy:** All user-facing strings stay Russian. Every CTA must be verb+noun (no standalone «Отмена»/«OK»/«Сохранить»/«Изменить»). Full copy table locked in spec §Copywriting Contract.
- **Preserved interactions:** Every `hx-*` attribute value, every route URL, every form `name=` attribute, every Jinja context variable name MUST remain byte-identical. Listed exhaustively in spec §Delivery Contract item 5.
- **Test gate:** `docker-compose exec app pytest tests/ -v` — all existing tests MUST pass after the rewrite.

### Claude's Discretion
- Icon delivery mechanism: inline-per-use OR Jinja macro in `templates/partials/icons.html` — both acceptable (spec §Delivery Contract item 3). **Recommendation:** SVG symbol sprite (see §Icon Strategy below) for the lowest-duplication, highest-maintainability approach. This is the researcher's recommendation; executor may still pick a macro.
- Narrow-viewport behaviour of the table: horizontal scroll OR stacked rows — executor's choice, must be documented (spec §Delivery Contract manual-QA item 12).
- Whether to add `hx-disabled-elt` on form submit buttons.
- Whether to wire a top-of-main HTMX progress bar or rely purely on opacity fade (spec explicitly says "pick opacity fade").
- Status badge implementation detail: render via Jinja macro vs. hand-rolled span — recommended macro (see §Component Patterns).

### Deferred Ideas (OUT OF SCOPE)
- Custom modal for delete confirmation — native `hx-confirm` stays.
- Any edit to FastAPI route handlers in `app/routers/`.
- Any rename of form field `name=` attributes or Jinja context variable names.
- Inline edit-row fragment design (deferred to 03-03 form validation plan which is still `[ ]` in ROADMAP).
- Real build pipeline, PostCSS, Tailwind, shadcn, React. Explicitly ruled out by CLAUDE.md.
- Dark mode. Not mentioned in spec; v1 is light-only.
- New page types (settings page, notifications page — those are Phase 4).

## CSS Architecture Strategy

**Recommendation:** Single-file, token-driven plain CSS. No preprocessor, no build step, no imports. All tokens on `:root`. ~500 lines max (spec §Delivery Contract item 1).

### Structure (top-to-bottom order inside `app.css`)

```
1. :root { --token: value; ... }      ~80 lines  (all tokens from spec)
2. *, *::before, *::after box-sizing reset
3. Base body, a, p, h1..h4 resets     ~20 lines
4. Skip link                          ~10 lines
5. Top nav (.nav-*)                   ~25 lines
6. Page container (main, .page-*)     ~10 lines
7. Stats grid + cards                 ~30 lines
8. Expiring widget                    ~30 lines
9. Filter controls                    ~30 lines
10. Table container + table + rows    ~60 lines
11. Status badges                     ~25 lines
12. Buttons + actions                 ~40 lines
13. Forms                             ~50 lines
14. Detail page                       ~40 lines
15. Empty states                      ~25 lines
16. 404 page                          ~15 lines
17. HTMX indicators + fadeIn keyframe ~15 lines
18. @media (prefers-reduced-motion)   ~10 lines
19. @media (max-width: 768px)         ~25 lines
```

**Why single file:** FastAPI's `StaticFiles` mount (`app.mount("/static", ...)` in `app/main.py`) serves files directly. Multiple files would require multiple `<link>` tags and multiple HTTP round-trips — wasted complexity for <500 lines. One file is idiomatic Linear/Vercel dashboards at this scale.

| Google Fonts CDN `<link>` | Zero build config, lowest friction, automatic WOFF2 + unicode-range subsetting, browser CDN caching, `display=swap` eliminates FOIT | Requires outbound HTTPS to `fonts.gstatic.com` from the operator's browser (app server doesn't fetch fonts — the browser does) | **CHOSEN** — internal dashboard; operators have HTTPS egress; htmx is already loaded via `unpkg.com` from the same `base.html`, so the external-CDN pattern is already established |
| Self-host in `static/fonts/` | Zero external dependency, works on air-gapped networks | Need to download WOFF2 files, check them into git (not a build step but repo bloat), write `@font-face` rules for both families × weight combinations, subset manually to avoid shipping Cyrillic+Latin+Vietnamese+etc. | **REJECTED** by spec but worth holding in reserve as a fallback if the environment audit below flags egress restriction |
| System font stack | Zero external dependency, zero bytes | Misses the "Linear look"; loses uniform cross-OS rendering | **REJECTED** by spec |

**Snippet to add to `templates/base.html` `<head>` (locked by UI-SPEC §Design System):**

```html
<link rel="preconnect" href="https://fonts.googleapis.com">
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
<link href="https://fonts.googleapis.com/css2?family=Inter:wght@400;600;700&family=JetBrains+Mono:wght@400&display=swap" rel="stylesheet">
```

**Order matters:** Insert BEFORE the existing `<link rel="stylesheet" href="{{ url_for('static', path='/css/app.css') }}">` so the font-family cascade is populated before `app.css` styles resolve.

**Cyrillic subset:** Google Fonts automatically serves the Cyrillic subset for Inter once `<html lang="ru">` is present (which it already is in `base.html`). No manual `&subset=` parameter is needed. Verified per Google Fonts' CSS2 API docs — the API uses `unicode-range` to auto-select subsets based on the text content on the page.

**Escape hatch (LOW confidence — not in spec):** If the operator network blocks `fonts.gstatic.com`, the only runtime-visible symptom will be system-font rendering (because of `display=swap`). The dashboard remains functional. If this is reported, the planner should open a follow-up task to self-host Inter + JetBrains Mono in `static/fonts/` with hand-written `@font-face` rules. **Recommendation:** Add a manual QA item to the plan: "Load dashboard from an operator workstation and confirm Inter is applied (not a system fallback)."

## Component Patterns for Jinja + HTMX

Jinja offers three mechanisms for reusable UI: `{% include %}`, `{% macro %}`, and template inheritance (`{% extends %}`). The existing codebase already uses `extends` (every page extends `base.html`) and `include` (`index.html` includes `partials/license_table.html`). For Phase 03.1 we add **macros** for the two reusable micro-components that appear in multiple templates.

### Pattern 1: Icon delivery via SVG symbol sprite + partial include

**Recommended over per-use inline copy-paste.**

Create `templates/partials/icons.html` containing a single `<svg>` element with `display: none` that declares every Lucide icon as a `<symbol>` with a stable `id`. Then include that partial ONCE in `base.html` right after `<body>`. Every usage site emits `<svg class="icon"><use href="#icon-alert-triangle"/></svg>` — two lines, no duplication, no macro overhead.

**Why this beats per-use inline SVG:**
- Every icon path is defined once, reducing `index.html` + `partials/license_table.html` bloat (the table has per-row status icons — inline would bloat every row).
- Stroke/fill inherit from CSS via `currentColor`, so status-badge colors cascade naturally.
- Zero JS. `<use>` is pure SVG spec.
- Browser caches the symbol once per page load.

**Why this beats a Jinja macro `{{ icon('alert-triangle') }}`:**
- A macro still emits the full SVG path bytes at every call site, which bloats the HTMX response body for the table partial.
- A symbol sprite ships the full icon set even if only 6 are used on the current page, but that's ~4KB total for all 12 Lucide icons — dwarfed by htmx itself.

**Tradeoff:** Symbol sprite requires a `viewBox` on the `<symbol>` declaration (easy — Lucide SVGs use `viewBox="0 0 24 24"` uniformly). The `<svg class="icon"><use href="#icon-X"/></svg>` pattern is slightly more verbose at call sites than `{{ icon("X") }}` but the gain in reuse outweighs it.

**Fallback:** If the executor prefers a macro (per spec §Delivery Contract item 3 — both acceptable), they may implement `templates/partials/icons.html` as:

```jinja
{% macro icon(name, size=16, class="") %}
  <svg class="icon {{ class }}" width="{{ size }}" height="{{ size }}" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2" stroke-linecap="round" stroke-linejoin="round">
    {% if name == "alert-triangle" %}<path d="m21.73 18-8-14a2 2 0 0 0-3.48 0l-8 14A2 2 0 0 0 4 21h16a2 2 0 0 0 1.73-3Z"/><path d="M12 9v4"/><path d="M12 17h.01"/>{% endif %}
    {# ... per icon ... #}
  </svg>
{% endmacro %}
```

and import with `{% from "partials/icons.html" import icon %}` at the top of each template that uses it.

**Where to find the SVG path data:** `https://lucide.dev/icons/{name}` — each icon page exposes a "Copy SVG" button that copies the full `<svg>` element. The internal `<path>`/`<circle>`/`<line>` elements are what the executor drops into either the symbol sprite or the macro branches.

### Pattern 2: Status badge via Jinja macro

The `.status-badge` pill appears in two places: the license table's Status column (`partials/license_table.html`) and the license detail page header (`license_detail.html`). Both usages take the same inputs (a status enum in {`active`, `warning`, `expired`}) and produce identical markup (pill with inline icon + Russian label).

**Recommended: macro in `templates/partials/_macros.html`** (leading underscore to mark it non-rendered):

```jinja
{% macro status_badge(status) %}
  {% if status == "active" %}
    <span class="status-badge status-badge-active">
      <svg class="icon"><use href="#icon-check-circle-2"/></svg>
      Активна
    </span>
  {% elif status == "warning" %}
    <span class="status-badge status-badge-warning">
      <svg class="icon"><use href="#icon-alert-triangle"/></svg>
      Скоро истекает
    </span>
  {% else %}
    <span class="status-badge status-badge-expired">
      <svg class="icon"><use href="#icon-x-circle"/></svg>
      Истекла
    </span>
  {% endif %}
{% endmacro %}
```

Imported at the top of `partials/license_table.html` and `license_detail.html` via `{% from "partials/_macros.html" import status_badge %}`. Called as `{{ status_badge(item.status) }}` and `{{ status_badge(status) }}`.

**Why macro over inline:** The `status-badge` markup is 4 lines and appears once per table row. The row fragment is HTMX-swapped, so duplicating 4×N lines per swap inflates the response body. A macro keeps it to `{{ status_badge(...) }}` per row. Plus the detail page reuses it.

**Row coloring survives HTMX swap** because `.status-active`/`.status-warning`/`.status-expired` classes are applied to the `<tr>` by `item.status_class` (already computed server-side in `enrich_licenses`), and the CSS rules target those classes directly. Swapping the tbody replaces the rows but the CSS keeps matching.

### Pattern 3: Skip link and base layout wrapping

Add to `templates/base.html`:

<body>

  {% include "partials/icons.html" %}
  <nav>...</nav>

    {% block content %}{% endblock %}

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Icon set | Custom SVGs, icon font, or hand-drawn glyphs | Copy Lucide static SVGs from lucide.dev | Battle-tested, uniform stroke/viewBox, free, used by Linear |
| Font delivery | Self-hosted WOFF2 + hand-written `@font-face` | Google Fonts CDN `<link>` | Spec-locked; auto-subsetting; `display=swap` handles FOIT |
| Focus ring | `:hover` / `:focus` without `:focus-visible` | `:focus-visible { outline: ... }` | `:focus-visible` is the 2026 baseline and avoids showing rings on mouse clicks while keeping them for Tab |
| Tabular number alignment | Fixed-width CSS hacks | `font-variant-numeric: tabular-nums` | Native CSS property, supported by Inter and JetBrains Mono via OpenType `tnum` feature |
| Sort indicator | Unicode `▲▼` characters | Inline Lucide `chevron-up` / `chevron-down` SVG | Current Unicode approach doesn't size or color uniformly; spec requires accent-600 color which CSS can't apply to Unicode glyphs reliably |
| Delete confirmation modal | Custom HTML modal + HTMX wiring | Native `hx-confirm` (already in place) | Spec explicitly defers custom modal to a future phase |
| CSS reset | Heavy normalize.css or CSS reset package | 3 lines: `*, *::before, *::after { box-sizing: border-box; }` + `body { margin: 0 }` | Phase-1 baseline; slim |
| Grid layouts | Float/inline-block hacks, `flex: 1 1 300px` chains | CSS Grid `grid-template-columns: repeat(3, 1fr)` for stats, `200px 1fr` for detail fields | Spec locks these; Grid is the idiomatic 2026 choice |
| Loading spinner for HTMX | Custom spinner component + `<img>` | `.htmx-request { opacity: 0.6 }` fade + `@keyframes fadeIn` on swap target | Spec says "pick opacity fade (simpler, no extra DOM)" |
| Accessibility testing | Hand-crafted checklists | `prefers-reduced-motion` media query + `:focus-visible` + `lang="ru"` + `<label for=>` (all already in templates) | Spec §Accessibility Contract enumerates exactly what's needed |

**Key insight:** This phase is a "no new dependencies" phase. Every recommendation above is native CSS or native HTML. The only two external dependencies (Google Fonts CDN and copy-pasted Lucide SVGs) are both runtime-static — no package manager, no npm install, no build.

## Common Pitfalls

### Pitfall 1: HTMX attributes re-ordered or paraphrased during class-name swap
**What goes wrong:** Executor opens `index.html`, sees a cluttered `<th>` with long `hx-get`, "tidies" it by moving attributes around, accidentally changes `hx-trigger="keyup changed delay:300ms"` to `delay:500ms` or drops the `hx-include` list.
**Why it happens:** CSS rewrite feels unrelated to HTMX, so executor doesn't read HTMX attributes carefully.
**How to avoid:** Plan step-level rule: "Do not touch any attribute whose name starts with `hx-`. If you need to edit an element, copy the attribute block byte-for-byte." Planner should include a pre-commit `grep -c 'hx-' templates/*.html` baseline count and verify the count is ≥ the same after changes.
**Warning signs:** `test_dashboard.py` lines 230–234 fail.

### Pitfall 2: Google Fonts blocked by corporate proxy, silent fallback
**What goes wrong:** Operator opens the dashboard; Inter never loads; system font renders; looks "fine-ish" but wrong.
**Why it happens:** `display=swap` is designed to mask font-load failures, which is usually good but here hides a regression.
**How to avoid:** Manual QA item: open the dashboard in DevTools → Network tab → filter `fonts` → verify both Inter and JetBrains Mono return 200. If they fail, open a follow-up to self-host.
**Warning signs:** Headings look slightly narrower than the Figma/spec reference; tabular numbers on the stat counters are not column-aligned (system fonts often lack `tnum`).

### Pitfall 3: Cyrillic contrast miscalculation
**What goes wrong:** Executor applies `--slate-500` (`#64748B`) as body text on `--slate-50` (`#F8FAFC`), gets 4.5:1 — technically AA but ONLY at that exact background. If anywhere gets a subtle darker hover (`--slate-100`), the muted text drops below 4.5:1.
**Why it happens:** The spec explicitly flags this: "Contrast muted text on slate-50 = 4.5:1 — AA (tight — do not darken background further)".
**How to avoid:** Never put `--slate-500` text directly on `--slate-100`. Muted text goes on `--surface` (`#FFFFFF`, 4.7:1) or `--slate-50` (4.5:1) only. On hover zones, use `--slate-700` for any text that must remain readable.
**Warning signs:** Manual contrast check with a browser devtools accessibility panel during QA.

### Pitfall 4: Jinja template file includes new partials without the executor registering them in pytest discovery
**What goes wrong:** New `templates/partials/icons.html` and `templates/partials/_macros.html` are created. Pytest discovers them fine (they're loaded at runtime by Jinja2), but if the executor places them in the wrong directory (e.g., `static/icons.html`) the include fails silently at render time.
**Why it happens:** The Jinja2Templates singleton in `app/templates.py` reads from `templates/` — any partial must live under that root.
**How to avoid:** Follow the existing convention (`templates/partials/license_table.html`). New partials go in `templates/partials/`. Verify by running `pytest tests/test_dashboard.py -k test_dashboard_loads -x` after adding the include.
**Warning signs:** `TemplateNotFound` Jinja exception at runtime, 500 error on the index page.

### Pitfall 5: Test copy conflict on the empty state
**What goes wrong:** Executor updates `index.html` to use the spec's `«Пока нет лицензий»` copy. `tests/test_dashboard.py:103` breaks because it asserts `"Лицензии пока не добавлены"`.
**Why it happens:** The copy is a test fixture, not just a display string.
**How to avoid:** The plan that updates the empty-state template MUST also update `tests/test_dashboard.py:103` in the same commit. Planner should flag this as a known test update.
**Warning signs:** Test failure with the literal old copy in the error diff.

### Pitfall 6: Inline `style="..."` attributes left behind
**What goes wrong:** `index.html` lines 77 and 83 have `style="cursor:pointer"` on `<th>`. `license_form.html` line 9 has `style="font-size: 1.75rem; font-weight: 600; margin-bottom: 24px;"` on the form `<h1>`. `index.html` line 97 has `style="margin-bottom: 1rem; display: inline-block;"` on the empty-state button. Executor swaps class names but forgets to delete inline styles; they override the new CSS.
**Why it happens:** Tunnel vision on `class="..."` attributes; inline styles are easy to miss.
**How to avoid:** Before declaring the phase complete, grep the templates for `style=`: `grep -rn 'style=' templates/` should return only genuinely required dynamic styles (ideally zero).
**Warning signs:** Visual regression where tokens are "right" but the element looks off-size.

### Pitfall 7: `.htmx-request` flicker on fast swaps
**What goes wrong:** When the server responds in <50ms (typical for SQLite), the `.htmx-request` class is added and removed so quickly that the opacity fade looks like a flash.
**Why it happens:** CSS transition from 1 → 0.6 → 1 in 10ms is imperceptible but visually jarring.
**How to avoid:** Use a `transition-delay: 100ms` trick OR accept it (spec says "opacity fade, simpler"). Recommended: accept, document the tradeoff.
**Warning signs:** Operators report "the table flickers when I type".

## Open Questions

1. **Empty-state test copy conflict**
   - What we know: `tests/test_dashboard.py:103` asserts `"Лицензии пока не добавлены"`. Spec copy is `«Пока нет лицензий»`.
   - What's unclear: Nothing — the conflict is concrete.
   - Recommendation: The plan that rewrites `index.html` empty state MUST also update `tests/test_dashboard.py:103` in the same commit. Planner should mark this as an explicit known test update step in the plan description (not a surprise).

2. **404 page copy routing**
   - What we know: The generic 404 copy per spec is `«Страница не найдена»`, but `app/routers/licenses.py:67-76` passes `title="Лицензия не найдена"` into `404.html`, and `tests/test_licenses.py:215` asserts `"Лицензия не найдена" in resp.text`.
   - What's unclear: Whether the spec's 404 copy is mandatory as the literal default or whether router callers may override via `title`.
   - Recommendation: Make the template use `{{ title if title else "Страница не найдена" }}` as the `<h1>`. The detail-not-found path continues to show "Лицензия не найдена" (test passes), and any other 404 shows "Страница не найдена". This is a better UX than a single generic copy and preserves the test verbatim. Flag in the plan.

3. **Narrow-viewport table behaviour**
   - What we know: Spec §Delivery Contract item 7 says executor picks horizontal scroll OR stacked rows.
   - What's unclear: Which choice the planner should prescribe.
   - Recommendation: **Horizontal scroll.** The table has 6 columns; stacking creates an awkward card-list UX on an internal ops tool that is almost always used on desktop. Horizontal scroll within `.table-container` with `overflow-x: auto` is a 2-line change and preserves all HTMX interactions. Planner should explicitly specify this in the plan so the executor does not deliberate.

4. **Google Fonts egress on operator network**
   - What we know: htmx is already loaded from `unpkg.com`, suggesting HTTPS egress is open.
   - What's unclear: Whether `fonts.googleapis.com` / `fonts.gstatic.com` specifically is reachable (some corporate proxies whitelist unpkg but not Google).
   - Recommendation: Add a manual QA item to the plan: "Open dashboard in browser → DevTools Network → verify Inter and JetBrains Mono both return 200. If blocked, open a follow-up plan to self-host WOFF2 files."

5. **Whether to add `docker-compose restart app` to the plan's done-condition**
   - What we know: Static files are served from the mounted `static/` directory, but the browser caches them by URL (no fingerprinting).
   - What's unclear: Whether a manual hard-reload is sufficient or whether the planner should prescribe a container restart.
   - Recommendation: Neither is needed by the server side. Add a manual QA note: "Hard-reload the dashboard page (Ctrl+Shift+R) after CSS changes land, to bust the browser cache." No container restart required.
